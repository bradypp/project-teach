Recover abandoned work

Created 13th Sept 2026 · 12:48

A worker claim must survive long enough to prevent duplicate work, but expire soon enough that a crashed worker cannot strand an event. A lease makes that tension explicit.

Follow the states Read a lease Claim atomically Know the boundary

Ownership is temporary until completion is durable

Lantern already owns an event once its inbox row is committed. A worker only borrows the right to process that row. The durable state must distinguish available work, a live claim, and completed work so another worker can recover after a crash.

A lease is a recoverable claim, not permanent ownership. Its expiry is the planned route from an interrupted attempt back to available work.

A crash trace should end in an actionable row

A useful debugging view keeps the event identity, lease owner, expiry and attempt together. The trace below is deliberately plain text: it is quick to paste into a ticket and still makes sense without a diagram. 

12:00:00  worker-a claims evt_204
            status=claimed  lease_until=12:00:30  attempt=3

12:00:11  worker-a exits before recording completion
12:00:29  worker-b scans -> evt_204 is still leased
12:00:31  worker-b scans -> lease expired; evt_204 is claimable

durable row
evt_204 | claimed | worker-a | 12:00:30 | attempt 3
FieldQuestion it answers
statusIs this row available, borrowed, complete or stopped?
lease_ownerWhich worker may renew or complete the current claim?
lease_untilWhen may another worker safely attempt a claim?
attempt_countIs this broad instability or one repeatedly failing event?

Make “find and claim” one database decision

Selecting a pending row and updating it in unrelated steps leaves a race: two workers can observe the same candidate. In SQLite, begin a write transaction, choose one eligible row, conditionally update it, and only treat a changed row as a successful claim. 

BEGIN IMMEDIATE;

UPDATE inbox_events
SET status = 'claimed',
    lease_owner = :worker_id,
    lease_until = :now_plus_30_seconds,
    attempt_count = attempt_count + 1
WHERE id = (
    SELECT id FROM inbox_events
    WHERE status = 'pending'
       OR (status = 'claimed' AND lease_until <= :now)
    ORDER BY received_at
    LIMIT 1
)
AND (status = 'pending' OR lease_until <= :now)
RETURNING *;

COMMIT;

The second eligibility check is intentional. It keeps the update honest if the selection rule later moves into a different query or database. After commit, the changed and returned row—not the earlier observation—is proof that this worker acquired the lease.

The remote side effect remains a separate problem

A lease recovers abandoned computation. It cannot prove whether an email or another remote effect succeeded immediately before the worker died. That boundary still needs a downstream idempotency key, a durable receipt, or reconciliation.

Your turn. Lantern takes 45 seconds to send a batch, but its lease lasts 30 seconds. Name the failure that can follow. Would you first extend the lease, renew it, reduce the batch, or change the effect contract—and what measurement informs that choice?
