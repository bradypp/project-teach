What an acknowledgement promises

Created 13th Sept 2026 · 00:47

A success response is a promise. Lantern should make that promise at the first point where losing the web process can no longer lose the event: immediately after the inbox row commits.

Name the promise Find the boundary Place it in code Try failure cases

First, name the promise

A webhook sender cannot see Lantern's internal state. It sees an HTTP response and decides whether delivery succeeded. Returning 2xx too early says “you can stop trying” while the only copy may still be in process memory.

HTTP gives us a useful distinction. A 202 Accepted response means the request was accepted for processing, not that processing finished. It is intentionally noncommittal about the final outcome. That semantic fits Lantern—but the status code cannot make an in-memory event durable. The implementation must earn the response.

Lantern's promise: once the sender receives success, Lantern owns a durable copy of the event and can continue processing without another delivery. It does not promise that the worker has already completed the side effect.

The commit is the hand-off

The important line is not “request received” or “job enqueued.” It is “the inbox transaction committed.” SQLite states that database reads and writes occur inside transactions; an explicit transaction lets Lantern treat all writes that establish ownership as one boundary.

Response pointIf Lantern crashes nextVerdict
Before validation The sender may retry malformed work forever. Reject clearly with a non-2xx response.
After appending to an in-memory queue The process restart erases the only copy. Too early.
After the inbox commit The worker can find the pending row after restart. The useful acknowledgement boundary.
After all business processing The event is safe, but slow work may make the sender time out. Correct but unnecessarily coupled.

Put the response after the durable write

This sketch leaves signature verification as an explicit prerequisite and keeps business work out of the request path. The database function returns only after its transaction commits. 

async def receive_event(request):
    raw_body = await request.body()
    verify_signature(raw_body, request.headers)
    event = parse_envelope(raw_body)

    result = inbox.record(
        provider="acme-pay",
        event_id=event.id,
        payload=raw_body,
    )  # committed before this call returns

    return Response.json(
        {"event_id": event.id, "state": result.state},
        status=202,
    )

A duplicate can still receive success because Lantern already owns the event. The next lesson makes that statement safe instead of hopeful.

Walk the two dangerous windows

  1. Crash before commit: no durable row exists and no success response was sent. The provider retries. This is recoverable.
  2. Commit succeeds, response is lost: the row exists, but the provider cannot know that. It retries. Lantern must recognize the repeated identity and avoid a second effect.
