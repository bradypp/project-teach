Retrieve evidence before writing the answer

Created 16th Sept 2026 · 21:44

A fluent explanation of the wrong incident is still wrong. Follow one question from a search query to a bounded evidence packet, then decide when Switchboard should decline to answer.

Retrieval supplies candidates

Retrieval-augmented generation (RAG) gives a model outside material to use when answering. For Switchboard, the material is versioned runbooks and incident notes. A search score says that a chunk resembles the query under a retrieval method. It does not establish that the chunk explains this incident, belongs to the right tenant, or is current.

Suppose “checkout errors after release 42” retrieves a current checkout runbook, an old connection-pool incident, and a billing outage that uses similar language. An answer built from all three can confidently mix unrelated causes. The retrieval stage has found candidates; evidence selection still has work to do.

Choose chunks that preserve the rule

Chunking splits documents into units the retriever can return. Fixed windows are easy to implement but may separate a runbook step from its prerequisite. Section-based chunks can keep “if the pool is saturated” attached to the restart instruction. Overlap can preserve a boundary but also return the same evidence twice.

Runbook v7 · pool saturationDiagnostic rule and required metricKeep, with section and version
Incident 18 · old pool limitHistorical hypothesisKeep only if current configuration matches
Billing timeout noteSimilar words, different serviceExclude from checkout evidence

Store an evidence envelope with document ID, section, version, tenant and the retrieved text. A citation should resolve to the exact version used. Otherwise a runbook edit can make yesterday’s answer impossible to audit.

Context engineering is choosing what survives

The model sees a finite input. Instructions, the question, tool schemas, prior turns and retrieved chunks all compete for space, and output needs a reserve. For a deliberately small teaching budget:

Total context allowance                 8,000 tokens
Instructions + tool schemas            -1,500
Question + useful history                -500
Reserved output                        -2,000
Available evidence                      4,000 tokens

At 800 tokens per chunk, five chunks fit exactly. Ten do not. Increasing retrieval depth can improve the candidate pool while leaving the final packet unchanged: retrieve broadly, rank, deduplicate, then pack. “Top k” for search and “chunks in the prompt” need not be the same number.

A simple packing policy takes high-ranked chunks while they fit. It can waste room on redundant evidence or skip a long but essential section. For this project, require service identity and incident time first, then select distinct supporting evidence. Record omitted evidence IDs so a failure can be traced to retrieval or packing.

Treat retrieved text as untrusted data. A runbook can contain a sentence that looks like an instruction to the agent. Tool permissions and tenant isolation must be enforced outside the model.

A citation is a claim to check

“Release 42 exhausted the pool” requires evidence about that release and the pool. A runbook saying pool exhaustion can cause errors supports a hypothesis, not a diagnosis. If no deployment metrics are available, the answer should say what is missing and propose a read-only check.

Distinguish an empty search, inaccessible evidence, stale evidence and conflicting evidence in the trace. They can all end in an abstention, but each points to a different repair. Prompt tuning cannot recover a source that never entered the packet.

Change one assumption

The right runbook is ranked sixth. Would you increase retrieval depth, increase the evidence budget, or change the ranking? First identify which stage excluded it. Then use the context lab to see why simply asking for more chunks can backfire.
