Why queues help

Created 10th Sept 2026 · 09:00

Fieldnotes export service · fictional learning project

Our export endpoint should accept a request quickly while a worker builds the file. A queue gives those two activities room to run at different speeds. It does not create processing capacity.

The decision · Capacity · Experiment · Failure boundaries

The planning question

Should POST /exports build the CSV before responding, or create a job that the user can check later? In this example project, a large export takes several seconds and multiple users may ask at once. We want a short acceptance response and a visible job status.

  • Producer: the request handler that submits a job.
  • Queue: waiting work that has not yet been taken by a worker.
  • Worker: the process that builds the export.
  • Job status: a separate explanation of what happened, such as pending, running, ready or failed.

The UI can now say “export requested” before the file exists. That is a promise about acceptance, not completion. Our plan must define what happens if a job never finishes; a fast response alone is not a successful export.

A burst is different from overload

Consider an invented workload: requests arrive at 8 jobs per second for 10 seconds, while workers finish 5 per second. During that burst, waiting work grows by roughly 30 jobs. If arrivals then stop, those jobs take roughly 6 seconds to drain. This simple calculation assumes uniform jobs and constant processing speed.

  • If arrivals settle at 2 per second, spare capacity drains the backlog.
  • If arrivals stay at 8 per second, a bigger queue only delays the point where waiting becomes unacceptable.
  • If export sizes vary, a job count alone hides how much work remains. Track waiting time as well as count.

Backpressure means feeding a capacity limit back to the producer. Our prototype will cap waiting jobs and show an explicit “try later” response when full. The capacity reference compares the available responses.

Make the limit observable

Python’s asyncio.Queue offers a bounded queue: awaiting put() waits for room; put_nowait() reports a full queue immediately. These are different admission policies. Python queue documentation.

This runnable experiment deliberately fills a two-slot queue without starting a worker. Predict whether the third job is accepted before running it:

import asyncio

async def main():
    pending = asyncio.Queue(maxsize=2)
    for job_id in ("export-a", "export-b", "export-c"):
        try:
            pending.put_nowait(job_id)
            print("accepted", job_id)
        except asyncio.QueueFull:
            print("try later", job_id)

    while not pending.empty():
        job_id = await pending.get()
        print("processing", job_id)
        pending.task_done()
    await pending.join()

asyncio.run(main())
Check the prediction

The first two jobs are accepted and the third gets “try later.” Removing an item creates room; marking it done accounts for completion. Those events are separate. This example prints instead of creating a file and runs everything in one process.

Start with the in-process experiment to expose the mechanism. Before promising durable acceptance to real users, design persistent job ownership and recovery. A broker also brings delivery semantics: for example, SQS standard queues can deliver a message again. SQS delivery documentation. The next lesson asks what a repeated attempt actually does.
