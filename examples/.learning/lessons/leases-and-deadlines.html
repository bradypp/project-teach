Who may finish this investigation?

Created 16th Sept 2026 · 22:32

A worker can lose ownership while its model call is still running. Follow a job through expiry, reclamation and cancellation, then make the result write enforce the same rules.

State names need transition rules

Switchboard accepts a job at 09:17:00 with a deadline of 09:17:30. Worker A claims it with generation 7 and a lease expiring at 09:17:10. At 09:17:12, worker B reclaims it with generation 8. A’s network call then completes. Both workers have an answer, but only B has the current claim.

A lease is time-bounded permission to work. A deadline bounds the whole job. A worker can have a valid lease on a job whose deadline has passed, so both conditions need checking. Use the database’s clock consistently for ownership decisions in this proposed design.

Enforce ownership at the write

A worker-side “am I still current?” check is insufficient. A can pass that check, pause, and then write after B takes over. Combine the check and mutation in one database operation. A zero-row result means the worker must treat its attempt as no longer authorised to complete the job.

-- Proposed result-write guard; illustrative schema, not a migration.
UPDATE investigations
SET status = 'completed', result = $1
WHERE id = $2 AND tenant_id = $3
  AND status = 'running'
  AND claim_generation = $4
  AND lease_until > clock_timestamp()
  AND deadline > clock_timestamp()
RETURNING id;

Cancellation can race with completion. Define the product rule: in this example, the first terminal transition committed wins. A cancellation update changes only an eligible nonterminal job; a completion update changes only a currently running one. Tell the client which state actually won. “Cancel requested” and “cancelled” are different facts.

A short claim transaction

PostgreSQL documents SKIP LOCKED as a way for queue-like consumers to skip rows another transaction has locked; the resulting view is unsuitable for ordinary consistent reporting. Source: SELECT locking clause.

Our proposed claim transaction selects eligible work, records a new generation and lease, then commits promptly. The worker performs slow tool calls after that transaction. Holding a row lock through a model call couples database contention to unpredictable network latency. Reclaim eligibility and attempt limits belong in this protocol too; selecting a row alone is not a durable claim.

Spend the remaining time

At 09:17:22 only eight seconds remain. Reserve two seconds for support checking and storing a result: the next tool call gets at most six seconds, even if its usual limit is ten. If no budget remains, the worker should produce the chosen expired or partial-result outcome rather than start more work.

Go’s context mechanism propagates cancellation and timeouts to operations that accept it; the official database example also defers the cancellation function to release resources. Source: cancelling in-progress operations. In this project that cooperation reduces wasted work, while the result-write guard still protects against late completion.

Try the race

Pause A after it receives a tool result. Expire its lease, let B claim generation 8, and then allow A to run its update with generation 7. Expect zero updated rows. Next cancel the job before B writes and check that completion also fails. These tests establish platform behaviour; they do not establish answer quality.
