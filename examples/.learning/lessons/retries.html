When a retry repeats a side effect

Created 12th Sept 2026 · 18:11

Fieldnotes export service · fictional learning project

reliability

A timeout tells us that an answer did not arrive in time. It does not tell us whether the export was created. Retrying safely requires a definition of “the same job.”

Failure window · Identity · Experiment · Contract

The next planning decision

A worker writes exports/job-42.csv, then crashes before reporting completion. Another worker retries the job. Should it create a second file, overwrite the first, return the existing result, or refuse to run?

We need a policy for that uncertainty before adding automatic retries. Idempotency describes the effect of repetition. The goal here is one logical export result even if processing is attempted more than once.

Identical input is not always identical intent

  • “Retry my export request” should keep the same operation key.
  • “Create another export with the same filters” should use a new key.
  • Reusing a key with different filters should be rejected, not silently return an unrelated file.

AWS’s idempotency design describes caller-provided request identifiers, parameter validation and recording the identifier together with the mutation. That provides a useful reference for this proposed contract; it does not make our implementation atomic automatically. Making retries safe with idempotent APIs.

Separate operation identity from an attempt

The following toy model makes repeat detection visible. It is deliberately synchronous and in memory. Predict what each call returns, then change the second call’s filters.

results = {}

def request_export(key, filters):
    signature = tuple(sorted(filters.items()))
    if key in results:
        previous_signature, path = results[key]
        if previous_signature != signature:
            raise ValueError("Key reused with different filters")
        return path
    path = f"exports/{key}.csv"
    results[key] = (signature, path)
    return path

print(request_export("job-42", {"month": "September"}))
print(request_export("job-42", {"month": "September"}))
Check the reasoning

Both calls return the same path. A changed month with the same key raises an error. This model records a path; it does not write a file or survive a restart. Two concurrent processes would not share this dictionary.

The dangerous gap between two writes

Imagine replacing the toy assignment with two real actions: write the file, then mark the database row complete. A crash between them leaves a result with no completion marker. Reversing the order leaves a different gap: a completed row with no result. Changing the order does not remove the gap.

  • For this project, investigate a deterministic output path plus verification that the expected file is complete before reusing it.
  • Define how workers claim jobs so two workers do not both publish an unfinished result.
  • Keep email notification outside the first milestone; it adds another external effect with its own duplicate policy.

These are design directions for the fictional project, not a claim that deterministic filenames alone provide exactly-once execution. The topic’s open questions keep the unresolved boundary visible.

Write the retry contract before the loop

SituationProposed behaviourWhy
Same key, same request, completeReturn its resultPreserve one logical export
Same key, changed requestReject the mismatchMake changed intent explicit
Still runningReport running statusA repeat need not start fresh work
Uncertain after crashReconcile stored state and outputA timeout is not proof of failure

A queue’s temporary ownership mechanism is another boundary. SQS visibility timeout hides received work temporarily; it is not a permanent completion acknowledgement. Read the visibility timeout documentation before translating this plan into that service.
