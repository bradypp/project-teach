Where the agent ends and the platform begins

Created 16th Sept 2026 · 21:44

An engineer starts an investigation, then closes the browser. Should the work stop? For Switchboard, it should continue. That choice gives the Go API and the graph worker different responsibilities.

One investigation, two kinds of state

An engineer asks: “Why did checkout errors spike after release 42?” The Go API authenticates the caller and accepts the investigation. A Python worker runs a LangGraph workflow that retrieves evidence, decides whether another read-only tool call would help, and drafts a cited answer. These components have different responsibilities even though they serve one user action.

The platform owns identity, admission, deadlines and durable job status. The graph owns the investigation’s current evidence and next step. A graph checkpoint describes progress inside an investigation; a job record describes the promise made to the caller. Neither automatically replaces the other.

Make acceptance mean something

For this project, POST /investigations returns 202 Accepted only after a job is committed. A client-generated request key is unique within a tenant. Repeating the request returns the same job ID, preventing a network retry from creating a second investigation.

OwnerState it keepsFailure it must handle
Go APITenant, request key, job ID, deadlineClient retries after a lost response
WorkerLease owner, expiry, attempt countProcess dies after claiming work
GraphEvidence IDs, tool outcomes, remaining budgetA tool times out midway through reasoning
Result storeAnswer, citations, terminal statusA stale worker tries to overwrite a newer result

Claim a job with an expiring lease. Renew it during execution and attach a monotonically increasing claim generation. A result write succeeds only if its generation still matches the current claim. Otherwise, a worker whose lease expired could finish late and overwrite the replacement worker’s answer.

Suppose worker A holds generation 7 and pauses during a model call. Its lease expires; worker B claims generation 8. When A returns, its answer may be perfectly usable, but its generation-7 write must fail. The store checks ownership, not answer quality. B is now responsible for finishing the job.

A request deadline is not a job deadline

In Go, an HTTP request context bounds work performed for that request. Our asynchronous contract deliberately ends that request after acceptance. The worker therefore reads an explicit job deadline instead of borrowing a context that disappears with the connection.

// Illustrative worker-side budget check; storage and error handling omitted.
remaining := time.Until(job.Deadline)
if remaining <= 0 {
    return ErrJobExpired
}
ctx, cancel := context.WithTimeout(workerContext, remaining)
defer cancel()
return runInvestigation(ctx, job)

If the investigation has 12 seconds left, a tool cannot receive a fresh 30-second allowance. Give it the smaller of its per-call limit and the remaining job time, leaving room to persist the result. Count retry time against that same budget.

Cancellation is cooperative. Every network call must receive a deadline, and every state write must reject expired ownership. Merely storing a deadline does not stop execution.

When a simpler design wins

A synchronous handler is a reasonable first prototype when one retrieval and one model call reliably fit the request budget. A durable job adds polling, leases and recovery work. It earns that complexity when investigations outlive connections, need several tools, or must survive worker restarts. The graph likewise earns its place through conditional steps and recoverable state; a fixed retrieve-and-answer chain may be enough at first.

Switchboard starts with read-only tools. If it later gains a rollback tool, a checkpoint cannot prove that a rollback did or did not happen before a crash. That operation needs its own idempotency and authorisation contract, plus a human approval boundary.

Try the failure on paper

A worker calls the model, loses its lease, then receives a complete answer. A second worker has already claimed the job. Which write must fail, and what field lets the store decide? Explain this before adding automatic retries.
