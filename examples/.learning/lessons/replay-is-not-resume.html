Replay is not resume

Created 16th Sept 2026 · 22:32

A paused investigation can run earlier code again. Trace a read-only tool call across an interruption, then decide which results and identities must survive recovery.

Two meanings of “continue”

A normal function continues from its current instruction because its process still holds the call stack. A durable workflow may reconstruct progress from stored state in another process. That reconstruction has a boundary: work before it may be remembered, repeated or deliberately recomputed.

LangGraph documents that resuming an interrupted node starts that node again from its beginning. Code before the interrupt can run again. That is narrower than saying every completed node always reruns. The checkpoint and the interruption location matter. Source: interrupt behaviour and replay rules.

A harmless read can still change the answer

At 09:20 the deployment feed says release 42 is active. The engineer answers a clarification at 09:24, after a rollback. A replayed read sees release 41. Both observations can be correct, but combining the old question with the new environment silently changes the investigation.

For Switchboard, choose an incident timestamp and pin source versions where possible. Record whether each tool result is a historical snapshot or a live observation. If a live refresh is necessary, give it a new evidence identity and explain the changed time scope. A cached tool result is useful only when its key includes the scope that makes the result valid.

Choose a node boundary around a decision

One large node is easy to sketch but makes a lot of work share a replay boundary. Smaller nodes expose intermediate states and failure locations, while creating more state to persist and maintain. Splitting every line is usually unhelpful; separate stages whose outputs are useful to recover or inspect.

Illustrative investigation stages
1. Resolve incident scope -> timestamp, tenant, service
2. Gather evidence       -> immutable evidence references
3. Ask clarification     -> resolved user intent
4. Draft answer          -> claims linked to evidence
5. Check support         -> answer or abstention

These are conceptual boundaries, not a complete LangGraph API example. Pin the framework and saver versions before implementing them. Test a crash at each boundary, rather than assuming the diagram establishes persistence guarantees.

LangGraph distinguishes thread-scoped graph checkpoints from cross-thread stores. For this design, keep investigation progress in its thread and use separate records for reusable data. An in-memory saver is useful for a demonstration but does not survive a process restart. Source: persistence systems and storage lifetime.

Design the replay test

Use a fake event source that returns v12 on its first call and v13 on its second. Pause the graph after retrieval, restart the worker, and resume. Inspect which evidence version is in the final answer and how many calls were made. Neither outcome is automatically correct: the intended snapshot policy determines the expected result.

Then move the read before and after the interruption boundary. Explain what changed, and why saving a graph checkpoint does not prove that every external operation happened exactly once.
