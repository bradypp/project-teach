An eval should tell you what broke

Created 16th Sept 2026 · 21:44

Switchboard gives a polished answer with a real citation—and still blames the wrong release. Build an evaluation that can distinguish missing evidence, bad reasoning and a platform failure.

Start with a case you can inspect

An evaluation is a repeatable test of behaviour against a stated expectation. For an incident assistant, “sounds helpful” is too vague. A useful case includes the question, tenant, incident timestamp, corpus snapshot, expected evidence and acceptable answer claims. Include cases where the correct behaviour is to say that the evidence is insufficient.

{
  "id": "checkout-pool-42",
  "tenant": "demo-shop",
  "question": "Why did errors rise after release 42?",
  "corpus_snapshot": "runbooks-fixture-v1",
  "required_evidence": ["deploy-42", "pool-metrics-42"],
  "must_not_claim": ["a rollback was executed"],
  "expected_outcome": "supported_hypothesis"
}

This fixture is synthetic. Its expected outcome is an author-reviewed contract for a test, not a measurement of the application’s quality. Keep a separate held-out set for judging changes; repeatedly tuning against the same cases makes them less informative.

Score the boundaries separately

BoundaryQuestionIf it fails
RetrievalDid the required evidence enter the candidate set?Inspect query, filters, corpus and ranking
Context packingDid it survive into the actual model input?Inspect budget, deduplication and truncation
Answer supportDoes each consequential claim follow from cited evidence?Inspect synthesis and support checking
Tool policyWere all tool calls allowed for this tenant and operation?Inspect enforcement outside the model
RuntimeDid the job finish within its limits with one durable result?Inspect deadlines, leases and retry policy

Exact checks work for source IDs, forbidden tool calls and terminal status. A rubric is needed for statements such as “the answer correctly distinguishes correlation from cause.” A model judge can help apply that rubric, but its decisions need calibration against human-reviewed examples. Record judge and prompt versions so a score change is interpretable.

Why a single average hides the bug

In a toy set of ten cases, eight have an answer in the corpus and two should abstain. Variant A answers seven of the eight correctly but invents answers for both unsupported cases. Variant B answers six correctly and abstains on both unsupported cases. Their raw correct-case counts are 7/10 and 8/10, but that still hides the operational trade-off: A misses less answerable material while fabricating in every unsupported case.

Report supported-answer performance and appropriate abstention separately. Slice by tenant, source freshness and incident type where enough cases exist. With only two unsupported cases, the observed 0/2 versus 2/2 is a useful debugging signal, not a precise estimate of future performance.

Run a comparison you can explain

  1. Freeze the corpus snapshot, cases, model settings and tool fixtures.
  2. Change one policy, such as context packing. Save candidates and packed evidence IDs for both runs.
  3. Inspect changed outcomes, especially new unsupported claims and policy violations.
  4. Repeat stochastic runs when outcomes vary. Report spread and failures, not just the best run.
  5. Promote the policy only after reviewing the held-out cases and operational cost.

An offline suite gives repeatable conditions. It does not reproduce every live outage, changing document or adversarial input. Production traces supply future test cases after appropriate redaction; they should not silently become a training set for the same evaluation.

Choose the next experiment

A required source appears in retrieval results but is absent from the model input. The answer invents a cause. What would you hold fixed, what would you change, and which intermediate result would prove your fix reached the right stage?
