A reliable investigation, end to end

Created 16th Sept 2026 · 21:44

Switchboard connects a durable platform request to a bounded evidence-gathering workflow. This page brings the lessons together around the contracts that make failures diagnosable.

Follow the promise

The Go API promises to track accepted work. The graph promises to spend a bounded amount of time gathering relevant evidence. The answer promises that its claims can be traced to that evidence. Each promise needs an observable boundary and a failure outcome.

Decisions for the first version

  • Use read-only deployment and runbook tools. Keep permissions in the tool service.
  • Persist jobs before acknowledging them; make request keys tenant-scoped.
  • Record candidate IDs separately from packed evidence IDs.
  • Require citations and allow an explicit insufficient-evidence outcome.
  • Evaluate each boundary before spending time on a more elaborate agent loop.

The costs are additional state, a worker process and a test corpus to maintain. A single synchronous RAG call is easier to build and may be sufficient for a smaller product. This project deliberately explores the point where recovery and conditional tool use justify the extra machinery.

Read around the next decision

  • Where the agent ends and the platform begins — ownership, leases and deadlines.
  • Retrieve evidence before writing the answer — candidate selection and context budgets.
  • An eval should tell you what broke — isolate a failure before tuning a prompt.

Still to explore

How should a user cancel a running investigation? What must survive graph replay? How should a corpus update affect a job already in progress? These are follow-on implementation questions. This notebook teaches the design mechanisms; it does not claim a deployed backend or verified framework API.
