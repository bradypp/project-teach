1. A burst ends. What happens next?

Spare processing capacity drains pending work. Queue storage itself does not process jobs. Review the capacity model.

2. A submission times out. Which retry preserves its identity?

Keep the operation identity stable for a repeat attempt. Changed intent needs a new key. See identity and intent.

3. A worker wrote the file but crashed before marking ready. What do we know?

The failure window leaves uncertainty. Recovery needs to reconcile output and state. See the proposed retry contract.

4. Explain the overload response

Suppose a user submits an export while all waiting slots are occupied. Choose waiting or refusal, describe the UI response, and identify one trade-off.

Compare with worked reasoning

For our short-acceptance-response goal, temporary refusal makes saturation visible without holding the request open indefinitely. The UI can explain that the export was not accepted and allow a later retry. Waiting might suit an internal producer whose own progress should slow with worker capacity.

5. Transfer to a new side effect

The worker now emails a download link. Why might a stable file path still fail to prevent duplicate emails?

Compare with worked reasoning

File identity only addresses the file result. A crash after sending email but before recording it can repeat the notification. The new effect needs its own delivery contract and recovery design.
