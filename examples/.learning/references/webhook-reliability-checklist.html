Webhook reliability checklist

Created 13th Sept 2026 · 00:47

A compact implementation and review companion for Lantern. Every checked item should point to code, a constraint, a metric or a tested failure—not just an intention.

Boundary Identity Capacity Failure tests

1 · Acknowledgement boundary

  • Verify the signature against the unmodified request body before accepting ownership.
  • Reject invalid or unsupported envelopes with a deliberate non-2xx response.
  • Commit the durable inbox row before returning success.
  • Keep slow business logic outside the request path.
  • Document what the chosen success code promises; do not imply processing is complete.

Why the commit is the hand-off →

2 · Identity and retries

  • Use a provider-issued event ID or explicit idempotency key, scoped to its issuer.
  • Enforce one event per identity with a database uniqueness constraint.
  • Insert directly with conflict handling; avoid a separate check-then-insert race.
  • Return a compatible success response for a known, identical delivery.
  • Store enough integrity data to reject the same identity with a changed payload.
  • Choose and document how long deduplication identity is retained.

Why identity belongs to intent →

3 · Capacity and backlog

  • Give every in-memory queue a positive bound; keep accepted events in durable storage.
  • Define the durable backlog limit in rows, bytes, age, tenant quota, or a useful combination.
  • Apply rejection or shedding before committing and acknowledging new ownership.
  • Coordinate retry guidance with providers so overload does not become a retry storm.
  • Alert on depth, oldest-event age, arrival rate, drain rate and rejected intake.
  • Separate poison events from broad saturation with attempt counts and a dead-letter path.

Compare overload policies →

4 · Worker safety

  • Claim work so concurrent workers do not deliberately process the same row.
  • Recover rows abandoned by a crashed worker.
  • Give each external side effect its own idempotency or reconciliation contract.
  • Record attempt time, completion, last error and correlation identity.
  • Do not mark completion before the effect you mean to represent has succeeded.

5 · Failure tests worth keeping

Inject this failureExpected durable truth
Crash before inbox commitNo row, no success; provider remains responsible for retry.
Lose the response after commitRetry maps to the existing row and causes no second capture.
Deliver the same ID concurrentlyThe uniqueness constraint permits one canonical row.
Reuse an ID with another bodyLantern reports a mismatch instead of overwriting.
Stop the worker after acceptingPending rows survive and age/depth metrics rise.
Crash after a remote effectRetry is safe through downstream idempotency or reconciliation.
Fill the configured backlogNew work follows the documented reject, spill or shed policy.
Review prompt. Pick any success response in the system and finish this sentence with a database fact: “After this response, Lantern can prove …” If the sentence names only memory or intention, the boundary is not durable yet.
