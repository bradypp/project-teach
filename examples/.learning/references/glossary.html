Reliability glossary

Created 13th Sept 2026 · 00:47

The small vocabulary behind Lantern's reliability design. Each term says what it means here and points back to the lesson that develops it.

Acknowledgement At-least-once delivery Backpressure Deduplication Idempotency key Inbox Lease Oldest-event age Transaction boundary

Acknowledgement

A response telling the sender what Lantern has accepted responsibility for. In this project, success means the event is durably stored; it does not mean business processing has finished.

See how Lantern defines the promise →

At-least-once delivery

A delivery contract in which the sender retries uncertain outcomes, so a logical event may arrive more than once. Reliability comes from not losing accepted work and making repeats safe—not from assuming one request.

Trace the lost-response scenario →

Backpressure

The explicit behavior used when downstream capacity is exhausted. For Lantern that might mean rejecting before storage, spilling to another durable tier, or shedding work under a stated freshness contract.

Compare the policies →

Deduplication

Recognizing multiple deliveries as the same logical event and retaining one canonical inbox row. Deduplication stops repeated capture; it does not automatically make every downstream side effect exactly once.

See the boundary of the guarantee →

Idempotency key

A stable identifier supplied by the party that knows which attempts express one intent. Lantern uses the provider-scoped event ID as the intake key and stores a digest to expose changed content under that ID.

See why identity should express intent →

Inbox

A durable table of received messages and their processing state. It separates the short HTTP intake path from slower work and remains the source of truth after a process restart.

See the inbox in Lantern's full design →

Lease

A time-limited worker claim on durable work. While it is live, other workers leave the event alone; after expiry, they may recover work from a crashed or stalled owner.

Follow the claim through its states →

Oldest-event age

The elapsed time since the oldest unfinished event was received. It exposes lateness that a stable or falling queue count can hide.

Interpret age alongside depth and rates →

Transaction boundary

The all-or-nothing region around related database changes. Lantern's intake transaction establishes one durable event identity before the handler returns success; worker effects may require a different boundary.
