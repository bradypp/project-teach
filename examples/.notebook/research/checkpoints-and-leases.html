Do checkpoints replace job leases?

Created 16th Sept 2026 · 22:32

Investigate whether Switchboard can use graph persistence as its only recovery mechanism, or whether the Go service still needs a job ownership protocol.

Decision and scope

For the proposed self-hosted Go API and Python graph worker, which component owns accepted work, resumed graph state and permission to write the final result? Sources inspected on 16 September 2026: current LangGraph Python documentation, PostgreSQL 18 documentation and the Go cancellation guide. The example has no pinned backend dependencies or production deployment.

What the sources establish

SourceSupported findingBoundary
LangGraph persistenceCheckpointers retain thread-scoped graph state; stores serve cross-thread data.Persistence scope differs from a public job status contract.
LangGraph interruptsAn interrupted node restarts from its beginning on resume.Earlier work inside that node may run again.
PostgreSQL lockingQueue-like consumers can skip rows locked by other transactions.Skipping locks does not itself define a lease or retry policy.
Go cancellationContext lets operations observe cancellation or a timeout.Our proposed ownership guard still decides whether a late write is accepted.

The sources describe complementary mechanisms, not contradictory advice. The right comparison is which promise each mechanism enforces.

Three viable designs

DesignBenefitCost or condition
Synchronous Go request and one model callSmall operational surfaceSuitable while useful work fits the request lifetime; recovery is limited
Go job store plus graph checkpointerExplicit ownership and inspectable graph progressTwo state systems require identity mapping and reconciliation
Managed graph runtime behind the Go APIMay delegate persistence and run managementVerify the chosen service’s admission, cancellation and concurrency guarantees before recreating them

These are project-level alternatives inferred from the mechanisms. This investigation does not benchmark them or claim that every hosted runtime requires a second custom queue.

Proposed choice for Switchboard

Keep a tenant-scoped job record for admission, deadline, claim generation and terminal status. Associate it with a graph thread for evidence and intermediate reasoning. Use a stable mapping that cannot cross tenants. A checkpoint records progress; the result update must still prove current ownership under our worker design.

The two stores can disagree temporarily. A graph may finish before the job status is updated. Recovery should recognise an already persisted result and reconcile status without paying for another model call. Conversely, a terminal cancellation should prevent a resumed worker from publishing a late answer. Define these cases before choosing retry loops.

What would confirm or change this choice?

  1. Pin framework, saver and database versions; inspect their actual recovery and transaction behaviour.
  2. Kill a worker after a tool result, after a checkpoint, and before the final status write. Record what repeats.
  3. Race two claims and a cancellation. Confirm that exactly one permitted terminal transition wins.
  4. Test source-version drift on replay and tenant checks on every evidence lookup.
  5. If a managed runtime already provides these contracts, remove redundant ownership machinery rather than maintaining two competing authorities.

Limitations

No implementation, fault-injection run or throughput benchmark was performed for this notebook. Tool side effects need their own idempotency design; graph recovery alone is not evidence of exactly-once execution. Recheck when the deployment model, checkpoint backend, framework version or tool permissions change.
