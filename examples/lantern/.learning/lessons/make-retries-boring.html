Make retries boring

Created 13th Sept 2026 · 00:47

Retries are normal when the sender cannot observe your commit. Give each intent a stable identity, enforce it in storage, and make the repeated path an ordinary result.

The ambiguity Stable identity SQLite implementation What this does not solve

A lost response creates ambiguity

Imagine Lantern commits evt_204, then the network drops its 202. The provider observes a timeout. It cannot tell whether nothing happened or whether everything up to the response happened, so retrying is the sensible action.

Identity belongs to the intent

A payload hash is useful for integrity, but it is a poor primary identity: two intentional events can have the same fields. Prefer the provider's stable event ID, scoped by provider or account. AWS makes the same design argument for caller-provided request identifiers: the caller can state which attempts belong to one intent.

Invariant: for one (provider, event_id), Lantern stores one canonical payload. A repeat with the same digest is harmless. The same ID with a different digest is a conflict worth surfacing, not silently overwriting.

Put this invariant in a uniqueness constraint. A separate “look first, then insert” check leaves a race where two handlers both see nothing and both proceed.

Let SQLite arbitrate the race

CREATE TABLE inbox_events (
    id             INTEGER PRIMARY KEY,
    provider       TEXT NOT NULL,
    event_id       TEXT NOT NULL,
    payload        BLOB NOT NULL,
    payload_sha256 TEXT NOT NULL,
    received_at    TEXT NOT NULL,
    processed_at   TEXT,
    UNIQUE (provider, event_id)
);

SQLite's UPSERT can turn a uniqueness conflict into a no-op. The transaction keeps the insert and conflict inspection together; the digest detects reused identity with changed intent. 

from dataclasses import dataclass
from hashlib import sha256

@dataclass(frozen=True)
class RecordResult:
    state: str              # "stored" or "duplicate"
    inbox_id: int

def record(connection, provider, event_id, payload):
    digest = sha256(payload).hexdigest()

    with connection:       # commit on success; rollback on exception
        inserted = connection.execute(
            """
            INSERT INTO inbox_events
                (provider, event_id, payload, payload_sha256, received_at)
            VALUES (?, ?, ?, ?, CURRENT_TIMESTAMP)
            ON CONFLICT(provider, event_id) DO NOTHING
            RETURNING id
            """,
            (provider, event_id, payload, digest),
        ).fetchone()

        if inserted:
            return RecordResult("stored", inserted[0])

        existing = connection.execute(
            """SELECT id, payload_sha256 FROM inbox_events
               WHERE provider = ? AND event_id = ?""",
            (provider, event_id),
        ).fetchone()

        if existing[1] != digest:
            raise IdempotencyConflict(event_id)

        return RecordResult("duplicate", existing[0])

Deduplicating intake is not exactly-once processing

The unique inbox row prevents duplicate capture. A worker can still crash after causing an external side effect but before recording completion. That later boundary needs its own strategy: an idempotency key understood by the downstream service, an atomic local transaction, or reconciliation.
