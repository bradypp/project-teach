Reliable webhook delivery

Created 13th Sept 2026 · 00:47

Reliable webhook intake is three linked contracts: retain before acknowledging, recognize repeated intent, and stop accepting work when retention or processing capacity is exhausted.

Mental model Key takeaways Lantern design Still to explore

Summary

Delivery is not one moment. The provider attempts a request, Lantern takes durable ownership, and a worker eventually applies an effect. Networks and processes can fail between every pair of those facts. A reliable design makes each transition recoverable without pretending it can eliminate uncertainty.

Three gates, in order

Read the diagram from the failure edges. A rejection leaves ownership with the provider. A lost success response causes a duplicate, which the unique key absorbs. A worker crash leaves a pending row for retry. The remaining hard case is an external effect that succeeds just before the worker crashes; that effect needs its own idempotency or reconciliation.

Key takeaways

  • An HTTP success code communicates a boundary; choose it from the durable fact you can defend.
  • At-least-once delivery is practical when repeats are safe and observable.
  • A provider-scoped event ID expresses intent better than guessing from payload equality.
  • A uniqueness constraint closes the race that an application-level pre-check leaves open.
  • Queue limits require an overload policy; they do not manufacture worker throughput.
  • Measure oldest-event age as well as depth so stale work cannot hide in a stable count.
