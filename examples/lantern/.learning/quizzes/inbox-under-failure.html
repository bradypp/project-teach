Lantern inserts an event into an in-memory queue, returns 202, then the process crashes before SQLite is touched. Who owns recovery?
A hint

Ask which copy survives the process, then ignore what the code intended to do next.

Why

The sender was told to stop retrying, but Lantern's only copy died with the process. Acknowledgement should follow the durable inbox commit. See The commit is the hand-off.

Two handlers receive evt_204 concurrently. Which design closes the race with the least application choreography?
A hint

Which layer can arbitrate both writes at the exact point the invariant is enforced?

Why

A uniqueness constraint makes the identity invariant indivisible from the write. A pre-check leaves time for another handler to act. See Let SQLite arbitrate the race.

Lantern already stored evt_204. The same provider sends that ID again with a different payload digest. What is the safest default?
A hint

The same key now appears to name two different intentions. Avoid guessing which one is real.

Why

Quiet overwrite destroys evidence; quiet discard hides a broken contract. Preserve the first committed fact and make the mismatch observable. See Identity belongs to the intent.

Arrivals remain at 90 events per second while the worker completes 60. What happens after adding an unbounded queue?
A hint

A buffer changes when work waits, not how quickly the worker finishes it.

Why

Sustained difference accumulates: 90 − 60 = 30 new pending events each second. Capacity requires a limit and policy. See The backlog is subtraction over time.

The worker sends an email, then crashes before setting processed_at. On restart, what can Lantern prove—and what extra contract would make retry safe?
Compare your reasoning

Lantern can prove that the event remains pending; its local transaction cannot prove whether the email service acted. Pass a stable effect key such as email:evt_204 to a service that honors idempotency, or reconcile against a durable downstream receipt before retrying. Intake deduplication alone does not solve this window. Revisit what deduplication does not solve.

Lantern's backlog limit is reached. Choose reject, spill, or shed for this project, and state the condition that makes your choice honest.
Compare your reasoning

A strong answer names the ownership boundary and loss contract. For Lantern's first slice, rejecting before storage with a temporary failure is defensible only if the provider retries and retry pressure is bounded. Spill is stronger when every event must be retained; shed is valid only for explicitly disposable work. Compare the overload policies.
