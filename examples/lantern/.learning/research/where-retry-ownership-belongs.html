Where should retry ownership live?

Created 14th Sept 2026 · 18:30

The durable inbox should own retry state because it can distinguish accepted work from completed work after a process failure.

Scope Findings Implications Sources Limitations

Scope

This investigation compares the boundaries already described in the Lantern example: receipt acknowledgement, durable inbox state and worker execution.

Findings

Acknowledgement proves that the event crossed the receiver's durability boundary; it does not prove that downstream work finished.

Lease-based recovery lets the inbox make interrupted work eligible again without asking the sender to reconstruct local execution state.

The project model therefore supports one owner for pending, leased, completed and failed states: the durable inbox.

Implications

  • Workers claim durable records rather than receiving untracked, in-memory jobs.
  • Retry timing and attempt counts remain observable across worker restarts.
  • Stable event identity can prevent a sender retry from creating independent work.

Sources

  • Lantern project plan — defines the example's receiver, inbox and worker boundaries.
  • Reliable webhook delivery — consolidates the current project model.

Limitations and recheck conditions

This conclusion is scoped to the example's database-backed inbox. Recheck it if delivery moves to an external broker that becomes the authoritative retry owner.
